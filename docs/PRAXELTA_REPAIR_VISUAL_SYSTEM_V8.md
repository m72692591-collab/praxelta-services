## Граница изменения

V8 продолжает существующую продуктовую, страховую, supplier и T‑Бизнес архитектуру. Проект не создаётся заново. Изменение касается визуального языка, UX-последовательностей, capability-driven отображения и безопасного standalone-прототипа.

`main`, GitHub Pages, реальные заявки, реальные платежи и production-конфигурация этим изменением не затрагиваются. Концептуальный знак в прототипе не является утверждённым логотипом.

## Идея

**Electric Atelier** соединяет надёжность инженерного сервиса и эмоциональность современного цифрового продукта. Интерфейс должен быть ярким, но цвет всегда кодирует смысл:

- cyan — подтверждённая прозрачность и информационное состояние;
- electric blue — основное действие;
- violet — процесс, расчёт и промежуточный статус;
- magenta — брендовый акцент, не системная ошибка;
- lime — выгода, подтверждение и успех;
- amber — внимание, банковский или финансовый контекст;
- red — блокировка, риск и критическая ошибка.

## Визуальные правила

1. Тёмная глубокая основа, светящиеся акценты и локальное glassmorphism.
2. Карточки имеют контрастную границу; стекло не должно ухудшать читаемость.
3. Один экран — одно главное решение и не более одной доминирующей CTA.
4. Финансовые суммы не маскируются декоративными элементами.
5. Работа, детали, доставка, скидка, комиссия и возврат отображаются раздельно.
6. Анимация короткая и функциональная. Обязателен `prefers-reduced-motion`.
7. Focus ring — контрастный lime; keyboard flow должен быть последовательным.
8. Русский текст естественный, без неподтверждённых обещаний и искусственных метрик.

## Capability-driven UI

Фронтенд не имеет права самостоятельно объявлять возможность активной. Каждый финансовый или страховой элемент получает состояние от backend registry:

```text
unknown   -> скрыть действие и показать нейтральное объяснение
checking  -> loading
active    -> разрешить действие
blocked   -> показать точную причину и безопасную альтернативу
stale     -> потребовать обновления состояния
partial   -> показать только подтверждённую часть
```

Отдельно запрещены:

- PAN, CVV/CVC и банковские секреты во frontend;
- ручная отметка «оплачено»;
- подтверждение по скриншоту или push;
- получение мастером клиентских денег на запчасть;
- скрытая комиссия или скрытая наценка;
- показ способа оплаты, которого нет в capability registry.

## UX-потоки

### Заявка

```text
направление
→ описание
→ фото
→ город/район
→ предварительная оценка
→ выбор мастера или режима
→ подтверждение сметы
```

До диагностики цена обозначается как диапазон, а не обещанная окончательная сумма.

### Запчасть

```text
диагностика
→ совместимость
→ предложения поставщиков
→ публичная цена
→ партнёрская цена
→ скидка уровня мастера
→ цена клиенту
→ раскрытие supplier CPS
→ подтверждение клиента
→ оплата
→ одноразовый QR
→ выдача конкретного SKU
```

### Оплата

```text
подтверждённая смета
→ официальный PaymentURL T‑Бизнеса
→ server-confirmed status
→ PARTS_LEG поставщику
→ LABOR_LEG после приёмки мастеру
→ MASTER_FEE ПРАКСЕЛЬТЕ
→ SUPPLIER_CPS ПРАКСЕЛЬТЕ
→ REFUND_LEG клиенту при возврате
```
